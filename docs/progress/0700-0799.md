## Iteration 714: native loop starts padded to 16 bytes

708's fury pack found bench.4's loop at 15 ms where it had been 7: the
kernel's shrinking moved the code after it, and the loop's start across a
16-byte line. Compilers align loops for that; this run-time compiler left
a hot loop's speed to where the code before it happened to end.

kernel-native.4: BEGIN, DO and ?DO pad HERE to the next 16 bytes with
nops before the loop's start (ALIGN-LOOP; NOP, lays one instruction of 1
to 8 bytes, two for 9 to 15), when LOOP-ALIGN-MAX - 15, a constant for
the sweep - allows. Falling into the loop runs the pad once per entry;
the back branch lands past it. Three things keep the alignment:
- the pad is recorded in the relative-field table as width 0 - field the
  pad's address, target its length - which SHORT-MOVE leaves alone (it
  is never in a moved region, and aims at nothing);
- a forward branch laid before a padded start stays long (SHORT-OK?,
  LAST-ALIGN beside 693's LAST-LEAVE): shortening it would move the loop
  back 3 or 4 bytes;
- a body that would be copied in place of its calls once its pads were
  out (INL-OK, and no longer than INL-LIMIT without them) loses them
  first (STRIP-PADS, GAP-OUT: the code after each pad moved back, every
  field and target re-aimed, the last pad first). An inlined copy lands
  anywhere, and the pads would only have made the body too long to copy.

Cost: the native shell's code 346,796 -> 351,925 bytes (+5,129, 1.5 %:
about 3.7 KB of nops, the rest branches kept long); the file 407,968 ->
412,096, one page. The kernel grew by the six words.

Speed, over layouts on the VM (tools/native-ab-layouts.py, 9 rounds,
pads 0-48), against 713: loop 0.998, fn 1.003, str 1.003, arith 1.000,

# relfsh: POSIX shell, написанный на форте

Я давно являюсь поклонником форта. Эта статья о том, что из этого в итоге выросло: relfsh — POSIX shell, написанный на форте. Это один статический файл размером 136524 байта, которому хватает 196 КБ памяти и который можно расширять изнутри, на форте, прямо во время работы. Под ним лежит небольшая форт система, которая компилирует сама себя, а ее движок для x86-64 собирается из исходника на форте ассемблером, который тоже написан на форте.

Больше всего в форте меня восхищает то, что один человек за несколько дней может поднять работающую форт систему на новой платформе. Целиком, вместе с компилятором, и при этом вся система достаточно мала, чтобы уместиться в одной голове.

В девяностых я познакомился с форт системой [sod32](https://lennartb.home.xs4all.nl/sod32.tar.gz), написанной [Lennart Benschop](https://lennartb.home.xs4all.nl/): маленькая виртуальная машина, которая исполняет двоичный образ, не зависящий от платформы. Мне она показалась очень красивой. У нее было два недостатка: ограничения, заложенные в сам дизайн, и скорость. RelF (Relative Forth) начинался как моя попытка их исправить. Попытка удалась, но прирост скорости оказался скромным, и через какое-то время я отложил проект.

Тем временем меня не отпускала другая мысль: shell — очень недооцененный инструмент. Большая часть «клея» в наших системах, то есть кода, который связывает между собой программы, файлы и процессы, — это ровно то, в чем shell хорош. Если писать такой клей на python, он становится длиннее, а каждая лишняя строка — это еще одно место для ошибки. Но и у shell есть два своих недостатка: расширять его можно только внешними программами, а структур данных в нем практически нет.

Здесь две идеи и встретились. Shell, написанный на форте, может быть маленьким и экономным, потому что таков сам форт. И его можно расширять изнутри, на самом форте, если дать ему подходящую встроенную команду.

Вот как это выглядит:

```
$ forth '2 3 + .'
5
$ forth 'S" examples/seq.4" INCLUDED'
$ seq 1 3 | while read n; do echo "line $n"; done
line 1
line 2
line 3
```

Встроенная команда `forth` дает доступ ко всей форт системе, на которой написан shell. В этом примере `seq` — новая встроенная команда, которая определена в дюжине строк на форте и после загрузки работает как любая другая. В каталоге examples есть еще хук для приглашения командной строки, TCP эхо-сервер и HTTP сервер — все на форте и все внутри shell.

Ошибка в таком коде завершает неудачей только одну команду, как это бывает с любой встроенной командой: `$?` равен 1, сообщение уходит в стандартный поток ошибок, а shell продолжает работать. Это касается и деления на ноль или обращения по плохому адресу: движок превращает аппаратное исключение процессора в фортовый THROW.

В остальном это обычный POSIX sh: конвейеры, списки, составные команды, функции, here-документы, все виды подстановок, управление заданиями, редактор командной строки с историей, поиском и автодополнением, а также `$'...'` и `set -o pipefail` из POSIX.1-2024.

Устроено все так:

```
./relfsh - один статический файл, 136524 байта
+------------------------------------------------+
| shell: парсер, исполнитель, редактор строки    |
|   shell.4  tree.4  edit.4          (форт)      |
+------------------------------------------------+
| форт: ядро, компилятор, расширения             |
|   kernel.4  extend.4  ...          (форт)      |
+------------------------------------------------+
| движок: 15456 байт кода x86-64, без libc       |
|   или движок на C, где есть компилятор C       |
+------------------------------------------------+
```

Shell и форт — это один двоичный образ с байт-кодом, а исполняет его движок. Движков два, и они исполняют один и тот же образ: переносимый, написанный на C, и написанный на ассемблере x86-64, который работает напрямую через системные вызовы. Все тесты прогоняются на обоих движках, и результаты должны совпадать.

Немного о форте, который лежит в основе.

- Шитый код на токенах: 64 однобайтовых опкода плюс дополнительные примитивы в виде двухбайтовых токенов (в RelF они называются «экранированными примитивами»). Высокоуровневые определения вызывают друг друга по *относительному* смещению — отсюда «Relative» в названии RelF. Благодаря этому образ не зависит от адреса загрузки, а его область в 4 МБ — это ровно дальность вызова.
- Свой образ для каждой разрядности ячейки: 8 или 4 байта, little-endian. Один образ работает на любой машине своей разрядности.
- Форт компилирует сам себя: `cross.4`, работая на предыдущем образе ядра, компилирует `kernel.4` в следующий, и получается байт в байт тот же образ. gforth, исполняя тот же кросс-компилятор, выдает те же самые байты — то есть проходит двойная компиляция разными компиляторами (diverse double compiling).
- Что я могу утверждать: система проходит тесты CORE — набор тестов за авторством John Hayes с дополнениями из набора тестов Forth 2012, всего 2136 проверок — на обоих движках и для обеих разрядностей. Помимо CORE в ней есть то, что понадобилось shell. Другие наборы слов я не заявляю, а недостающие слова можно определить через встроенную команду `forth`.

Движок для x86-64 написан на форте (`engine/relfasm64.4`) при помощи ассемблера x86-64, который тоже написан на форте (`forth/asm64.4`) и использует постфиксный синтаксис:

```
rax [ rbx 8 ] mov,       \ mov rax, [rbx+8]
r12 [ r13 ] mov,         \ mov r12, [r13]
```

Цепочка сборки выглядит так:

```
engine/cv8.c --cc--> relf64 (движок на C, один раз)
                        |
kernel.4 + cross.4 -----+--> kernel64.img  (воспроизводит себя)
                        |
relfasm64.4 + asm64.4 --+--> relfasm64     (15456 байт)
                            |
relfasm64.4, еще раз -------+--> relfasm64 (те же байты)
```

Движок на C собирается один раз и запускает ассемблер. Получившийся движок собирает сам себя повторно, и получаются те же 15456 байт. Вывод ассемблера сверяется с GNU as байт в байт на всех 456 формах инструкций, которые использует движок, а также на случайных инструкциях всех форм, которые ассемблер поддерживает. Именно так выяснилось, что `push`, `pop` и `xchg` с операндом в памяти молча собирались как инструкции с регистром. Это исправлено, и проверка случайными инструкциями теперь выполняется при каждой верификации.

Ближайший аналог, который я знаю, — lbForth, написанный Lars Brinkhoff: самокомпилирующийся метакомпилируемый форт, который раскручивается из нескольких строк на C.

Теперь о цифрах. Память в КБ, измерено при помощи tools/mem-profile.py:

```
                   резидентная  приватная
relfsh, движок asm         196        196
relfsh, движок C          1940        384
dash                      1968        100
busybox ash               1608        252
bash                      3704       1740
```

По резидентной памяти relfsh на своем движке меньше всех с большим отрывом: он не загружает библиотеку C. Если же считать только приватную память, dash использует вдвое меньше, чем relfsh.

Со скоростью нужно быть честным. Сначала shell: процессорное время относительно dash, медиана десяти раундов, в каждом из которых каждый shell прогонял каждую нагрузку (tools/bench-vm.py). В первой строке собственное время dash.

| процессорное время, раз от dash | loop | fn | str | arith | realistic | start |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| dash, мс | 4,1 | 2,6 | 2,8 | 3,0 | 3,4 | 1,4 |
| busybox ash | 1,1 | 1,2 | 1,1 | 1,3 | 1,3 | 0,93 |
| bash | 2,1 | 2,4 | 2,2 | 2,4 | 2,8 | 1,3 |
| relfsh, движок asm | 25 | 22 | 20 | 27 | 27 | 0,56 |
| relfsh, движок C | 26 | 23 | 21 | 28 | 28 | 1,1 |

Нагрузки: loop — 2000 итераций проверки и инкремента; fn — 600 вызовов функции; str — 400 итераций `${s##*/}`, `${s%/*}` и `case`; arith — 700 шагов фибоначчи по модулю; realistic — разбор опций, обрезка строк, `case`, арифметика и `set --`, 300 итераций; start — один запуск `sh -c true`. На запуск relfsh тратит чуть больше половины того, что тратит dash, но скрипты исполняет в 20–28 раз медленнее: это интерпретатор байт-кода, а dash написан на C.

Теперь RelF как форт: семь небольших программ, один и тот же текст на форте для всех трех форт систем и те же алгоритмы на C, go, python и ruby (bench/langs/run.py). Время в миллисекундах, лучшее из трех запусков, включая запуск процесса; результат каждого запуска сверяется с результатом C. Последняя колонка — среднее геометрическое отношений ко времени RelF.

Отдельно хочу рассказать о тестировании: от shell ждут очень точного поведения, и проверять его приходится с разных сторон.

- CORE: 2136 проверок, вывод обоих движков совпадает.
- Сам shell: 1033 проверки в 91 файле; 132 случая, где вывод сравнивается с bash; 421 конструкция во всех контекстах, против bash и dash; 48 случаев из POSIX, которые засчитываются только там, где все эталонные shell согласны между собой; набор тестов mrsh; 32 сессии через псевдотерминал для редактора строки и управления заданиями; примеры из самого стандарта POSIX, 64 штуки, с теми результатами, которые указаны в его тексте.
- Помимо наборов тестов: семь shell «голосуют» по 131 скрипту, и relfsh оказывается на стороне каждого уверенного большинства; 1000 случайных программ против dash и bash без единого расхождения; каждый тестовый скрипт, переписанный девятью способами, которые не должны менять его вывод; мутационное тестирование скомпилированного образа; тестовая обвязка, которую исполняет сам relfsh; сигнальные штормы, в которых отработал каждый trap и сошлась каждая сумма; и реальные скрипты — configure от zlib и от ncurses (32301 строка autoconf), у которого все 1041 сгенерированный файл совпадают с результатом dash, кроме мест, где autoconf записал, как echo каждого shell подавляет перевод строки.
- Каждое изменение проверяется на трех машинах — двух x86-64 и плате с ARMv7 — прежде чем попасть в репозиторий.

Чтобы не было завышенных ожиданий, хочу сразу оговорить, чего здесь нет.

- Это не полная система Forth 2012: только CORE и то, что нужно shell.
- Скрипты он исполняет медленно, цифры выше.
- Движок на ассемблере есть только для x86-64. Движок на C работает на x86-64, i386 и ARMv7, а под qemu — на AArch64 и RISC-V.
- Локалей нет, время shell показывает в UTC.

Предвижу вопрос о том, как все это делалось. Начиная с конца августа 2026 года большую часть кода, тестов и документации написал Claude, ИИ-модель, в нескольких сотнях пронумерованных итераций под моим руководством. Я ставил цели, принимал решения (тридцать из них записаны в docs/QUESTIONS.md) и прогонял каждое изменение на своих машинах, прежде чем оно попадало в репозиторий. Журнал всех итераций, включая ошибки, лежит в docs/PROGRESS.md.

Попробовать можно так:

```
git clone https://github.com/kt97679/relf
cd relf && make
./relfsh
make verify            # все наборы тестов, займет несколько минут
```

# relfsh: POSIX shell, написанный на форте

Я давно люблю форт, и эта статья — о том, что из этого в итоге выросло: relfsh — POSIX shell, написанный на форте. На x86-64 это один статический файл размером 139036 байт; в простое он занимает около 210 КБ памяти, а расширять его можно изнутри, на форте, прямо во время работы. Под ним лежит небольшая форт система, которая компилирует сама себя, а ее движок для x86-64 собирается из исходника на форте ассемблером, который тоже написан на форте.

Больше всего в форте меня восхищает то, что один человек за несколько дней может поднять работающую форт систему на новой платформе. Целиком, вместе с компилятором, и при этом вся система достаточно мала, чтобы уместиться в одной голове.

В девяностых я познакомился с форт системой [sod32](https://github.com/lennart-benschop/sod32), написанной [Lennart Benschop](https://github.com/lennart-benschop): маленькая виртуальная машина, которая исполняет двоичный образ, не зависящий от платформы. Мне она показалась очень красивой. У нее было два недостатка: ограничения, заложенные в сам дизайн, и скорость. RelF (Relative Forth) начинался как моя попытка их исправить. Попытка удалась, но прирост скорости оказался скромным, и через какое-то время я отложил проект.

Тем временем меня не отпускала другая мысль: shell — очень недооцененный инструмент. Большая часть «клея» в наших системах, то есть кода, который связывает между собой программы, файлы и процессы, — как раз то, с чем shell справляется лучше всего. Если писать такой клей на Python, он становится длиннее, а каждая лишняя строка — это еще одно место для ошибки. Но и у POSIX shell есть два недостатка. Расширять его можно только внешними программами (bash, ksh93 и zsh умеют подгружать встроенные команды, но это код на C, собранный под заголовки конкретного shell), а структур данных в нем практически нет.

Здесь две идеи и встретились. Shell, написанный на форте, может быть маленьким и экономным, потому что таков сам форт. И его можно расширять изнутри, на самом форте, если дать ему подходящую встроенную команду.

Вот как это выглядит:

```
$ ./relfshasm64
$ forth '2 3 + . CR'
5
$ forth 'S" examples/seq.4" INCLUDED'
$ type seq
seq is a shell builtin
$ seq 1 3 | while read n; do echo "line $n"; done
line 1
line 2
line 3
```

Встроенная команда `forth` дает доступ ко всей форт системе, на которой написан shell. В этом примере `seq` — новая встроенная команда: восемь строк на форте в файле `examples/seq.4`, которых нет в самом бинарнике; файл подгружается на лету, и дальше команда ведет себя как любая другая встроенная. В каталоге [examples](https://github.com/kt97679/relf/tree/article-2026/examples) есть еще хук для приглашения командной строки, эхо-сервер на TCP и HTTP-сервер — все на форте и все внутри shell. Если записать строку с `forth` и полным путем к `seq.4`, в файл, на который указывает переменная `$ENV`, команда будет доступна при каждом запуске интерактивного shell.

Для тех, кто не знаком с фортом: программа на форте — это последовательность слов, которые берут аргументы со стека и кладут результаты на стек, поэтому запись постфиксная: `2 3 +` оставляет на стеке 5, а `.` его печатает. Новое слово определяется между `:` и `;`. `' DO-SEQ` — это ссылка на слово, а `S" seq"` — строка.

Вот сам `seq`, без двух строк `SEQ-NUM`, которые читают десятичное число. В нем виден весь интерфейс встроенной команды: аргументы она получает через `ARGC` и `ARGV@`, код возврата записывает в `LAST-STATUS`, а имя ей дает слово `BUILTIN`.

```
: DO-SEQ ( --- )
  ARGC @ 3 < IF S" usage: seq FIRST LAST" ERR-TYPE ERR-NL 2 LAST-STATUS ! EXIT THEN
  2 ARGV@ SEQ-NUM 1+  1 ARGV@ SEQ-NUM
  2DUP > IF ?DO I N>STR DUP CSTRLEN TYPE CR LOOP ELSE 2DROP THEN
  0 LAST-STATUS ! ;
' DO-SEQ S" seq" BUILTIN
```

Ошибки, которые замечает сама форт система, завершают с ошибкой только эту команду, как у обычной встроенной команды: `$?` равен 1, сообщение уходит в стандартный поток ошибок, shell работает дальше. Это неизвестное слово и THROW, лишние или недостающие ячейки на стеке (shell восстанавливает стек), переполнение стека, например от бесконечной рекурсии, деление на ноль и обращение за пределы памяти shell (аппаратное исключение движок превращает в фортовый THROW), а также файл, который не удалось подключить. Но изоляции нет: все остальное, что делает фортовое слово, происходит внутри shell, и запись по неверному адресу в его памяти может его уронить — так же, как ошибочная загружаемая встроенная команда роняет bash.

В остальном это обычный POSIX sh: конвейеры, списки, составные команды, функции, here-документы, все виды раскрытий (тильды, параметров, команд, арифметики, имен файлов), управление заданиями, редактор командной строки с историей, поиском и автодополнением, а также `$'...'` и `set -o pipefail` из POSIX.1-2024.

Кроме любителей форта, он может оказаться полезен в трех случаях. Первый — минимальные окружения: на x86-64 статический shell без libc, по памяти близкий к статическому dash, но расширяемый на месте, может пригодиться в initramfs (сами утилиты при этом все равно придется взять, например, из busybox) или в контейнере без базового образа. Второй — скрипты, которым не хватает структур данных: недостающее можно дописать на форте в виде встроенных команд и вызывать без запуска новых процессов: [examples/map.4](https://github.com/kt97679/relf/blob/article-2026/examples/map.4) — это ассоциативный массив, `map set KEY VALUE`, `map get KEY` и `map keys`, в 33 строках кода на форте (без комментариев). Третий — учебный: на x86-64 вся цепочка, от ассемблера до shell, написана на форте и воспроизводит саму себя.

Устроено все так:

```
./relfshasm64 - один статический файл, 139036 байт
+------------------------------------------------+
| shell: парсер, исполнитель, редактор строки    |
|   shell.4  tree.4  edit.4          (форт)      |
+------------------------------------------------+
| форт: ядро, компилятор, расширения             |
|   kernel.4  extend.4  ...          (форт)      |
+------------------------------------------------+
| движок: 15760 байт для x86-64, без libc        |
|   или движок на C, где есть компилятор C       |
+------------------------------------------------+
```

Shell и форт — это один двоичный образ с байт-кодом, а исполняет его движок. Движков два, и они исполняют один и тот же образ: переносимый, написанный на C, и написанный на ассемблере x86-64, который работает напрямую через системные вызовы. На x86-64 оба движка проходят одни и те же тесты CORE (вывод совпадает байт в байт), тесты shell, сравнение с bash и сессии через псевдотерминал, а образы, которые они собирают, совпадают.

Немного о форте, который лежит в основе.

- Шитый код на токенах: 64 однобайтовых опкода плюс дополнительные примитивы в виде двухбайтовых токенов: экранирующий байт и номер примитива. Высокоуровневые определения вызываются по смещению от начала образа — отсюда «Relative» в названии RelF, — поэтому образ работает, куда бы его ни загрузили. Вызов слова из первых 16 КБ образа занимает два байта, откуда бы его ни вызывали; любой другой — три и дотягивается до 4 МБ, поэтому образ и живет в области размером 4 МБ. Ядро — это первые 9544 байта образа, так что любой вызов ядра двухбайтовый.
- Свой образ для каждой разрядности ячейки: 8 или 4 байта, little-endian. Один образ работает на любой поддерживаемой машине своей разрядности.
- Форт компилирует сам себя: `cross.4`, работая на предыдущем образе ядра, компилирует `kernel.4` в следующий, и получается байт в байт тот же образ. Сама по себе самосборка еще ничего не гарантирует. В лекции «Reflections on Trusting Trust» Ken Thompson показал, что компилятор можно научить вставлять закладку в собираемые им программы, в том числе в новые версии самого себя. Тогда закладка переживает любую проверку исходников: исходник чист, а бинарник нет. Защита — собрать тот же исходник другим, независимым компилятором и сравнить результаты. Этот метод, [diverse double-compiling](https://arxiv.org/abs/1004.5534), обосновал David A. Wheeler, а сама идея восходит к Henry Spencer. Здесь роль независимого компилятора играет gforth 0.7.3: исполняя тот же кросс-компилятор, он выдает те же самые байты. Значит, в ядре нет ничего сверх написанного в его исходнике, если только такой же закладки нет в самом gforth. Остальной образ и движок на ассемблере собирает уже сам RelF, а движок на C — компилятор C, так что проверка относится только к ядру.
- Система проходит тесты CORE — набор John Hayes ([tests/tester.fr](https://github.com/kt97679/relf/blob/article-2026/tests/tester.fr)) с дополнениями из набора Forth 2012, всего 2136 проверок — на обоих движках и для обеих разрядностей. Сверх CORE в ней есть то, что понадобилось shell; недостающие слова можно определить через встроенную команду `forth`.

Движок для x86-64 написан на форте ([`engine/relfasm64.4`](https://github.com/kt97679/relf/blob/article-2026/engine/relfasm64.4)) при помощи ассемблера x86-64, который тоже написан на форте ([`forth/asm64.4`](https://github.com/kt97679/relf/blob/article-2026/forth/asm64.4)) и использует постфиксный синтаксис:

```
rax [ rbx 8 ] mov,       \ mov rax, [rbx+8]
r12 [ r13 ] mov,         \ mov r12, [r13]
```

Цепочка сборки выглядит так:

```
engine/cv8.c --cc--> relf64 (движок на C, один раз)
                        |
kernel.4 + cross.4 -----+--> kernel64.img  (воспроизводит себя)
                        |
relfasm64.4 + asm64.4 --+--> relfasm64     (15760 байт)
                            |
relfasm64.4, еще раз -------+--> relfasm64 (те же байты)
```

Движок на C собирается один раз и запускает ассемблер. Получившийся движок собирает сам себя повторно, и получаются те же 15760 байт. Вывод ассемблера сверяется с GNU as байт в байт на всех 456 формах инструкций, которые использует движок, а на случайных инструкциях всех форм, которые ассемблер поддерживает, — с точностью до равнозначных кодировок. Ассемблер небольшой: он умеет только то, что нужно движку, а остальное отвергает.

Ближайший аналог, который я знаю, — [lbForth](https://github.com/larsbrinkhoff/lbForth), написанный Lars Brinkhoff: форт с метакомпилятором, который собирает сам себя, а раскручивается из нескольких строк на C. Сам себя собирает и SP-Forth — из своих исходников, с ассемблером на форте, — но он компилирует в машинный код x86, а RelF — в переносимый байт-код с отдельным движком.

Теперь о цифрах. Все измерено 28 сентября 2026 года на AMD Ryzen 7 PRO 8840HS (Ubuntu 24.04, регулятор частоты powersave) с dash 0.5.12, bash 5.2.21 и BusyBox 1.36.1 из Ubuntu (статическая сборка), а для сравнения еще и с dash 0.5.12, собранным статически с musl (musl-gcc -Os -static). Повторить замеры у себя можно командой `sh tools/bench-report.sh`: что для этого нужно, написано в начале скрипта, а то, чего у вас нет, скрипт пропустит.

Память в простое в КБ, по замерам [tools/mem-profile.py](https://github.com/kt97679/relf/blob/article-2026/tools/mem-profile.py):

```
                    резидентная  приватная
relfsh, движок asm          212        212
dash, статический           176        176
busybox ash, статический    812        148
dash                       1564        120
relfsh, движок C           1564        400
bash                       2808        292
```

Каждый shell читает свой /proc/PID/smaps: резидентная память — это сумма Rss, куда входят и страницы, общие с другими процессами, прежде всего библиотека C; приватная — сумма Private\_Clean и Private\_Dirty. Статический бинарник не загружает библиотеку C, поэтому relfsh на своем движке занимает резидентной памяти в 7–13 раз меньше, чем динамически собранные dash и bash, почти вчетверо меньше статического busybox и близок к статическому dash, который еще меньше. Приватная память — то, что добавляет каждая копия, и тут меньше всех у dash, а у relfsh на своем движке ее почти вдвое больше. Файл relfsh — 139036 байт против 169720 у статического dash, и в нем еще компилятор форта и редактор строки.

Сначала скорость shell: процессорное время (user+sys) относительно dash, медиана отношений по семи раундам, в каждом из которых каждый shell прогонял каждую нагрузку ([tools/bench-vm.py](https://github.com/kt97679/relf/blob/article-2026/tools/bench-vm.py)). Нагрузки подобраны так, чтобы собственный запуск dash (1,7 мс) занимал не больше десятой доли времени dash на каждой из них: loop — 50000 итераций проверки и инкремента; fn — 15000 вызовов функции; str — 10000 итераций `${s##*/}`, `${s%/*}` и `case`; arith — 17500 шагов вычисления чисел Фибоначчи по модулю; realistic — разбор опций, обрезка строк, `case`, арифметика и `set --`, 7500 итераций; start — один запуск `sh -c true`. В первой строке собственное время dash.

Скрипты relfsh исполняет в 29–42 раза медленнее dash: relfsh — интерпретатор, который сам исполняется виртуальной машиной, а dash — интерпретатор на C. Запускается relfsh примерно так же быстро. Статический dash запускается еще быстрее, но скрипты исполняет медленнее обычного: он собран с -Os и с musl, поэтому с ним имеет смысл сравнивать прежде всего память и время запуска. Движок на ассемблере исполняет скрипты лишь на 0–5% быстрее движка на C: оба упираются в то, как быстро процессор выполняет косвенные переходы один за другим, а смысл движка на ассемблере в том, что ему не нужна библиотека C. На форт-программах ниже разница больше, около 15%, хотя matrix и fannkuch быстрее на движке C.

Теперь RelF как форт: семь небольших программ, один и тот же текст на форте для всех трех форт систем и те же алгоритмы на C, Go, Python и Ruby ([bench/langs/run.py](https://github.com/kt97679/relf/blob/article-2026/bench/langs/run.py)). Отдельно хочу рассказать о тестировании: от shell ждут очень точного поведения, и проверять его приходится с разных сторон.

- CORE: 2136 проверок, вывод обоих движков совпадает.
- Сам shell:
  - 1079 проверок в 91 файле;
  - 132 случая, где вывод сравнивается с bash;
  - 422 случая, где небольшая конструкция стоит в каждом из контекстов — после `;` и `&&`, в функции, цикле, `if`, подоболочке и подстановке команды, в конвейере, с перенаправлением, в фоне, — в сравнении с bash и dash;
  - 48 случаев из POSIX, которые засчитываются только там, где все эталонные shell согласны между собой;
  - набор тестов из [mrsh](https://github.com/emersion/mrsh), другого маленького POSIX shell;
  - 45 сессий через псевдотерминал для редактора строки и управления заданиями;
  - примеры из самого стандарта POSIX, 64 штуки, с теми результатами, которые указаны в его тексте.
- Помимо наборов тестов:
  - 131 сравнительный скрипт прогонялся через семь других shell — dash, bash, yash и mksh в режиме POSIX, posh, ksh93 и busybox ash: там, где согласны хотя бы пятеро (112 скриптов), relfsh всегда с большинством; в остальных 19 голоса разделились — на расширениях, новинках POSIX.1-2024 вроде `$'...'` и том, что стандарт оставляет на усмотрение реализации;
  - эти же 131 скрипт, каждый переписанный до девяти раз так, чтобы вывод не менялся, — всего 1170 вариантов;
  - 1000 случайных программ от генератора по грамматике shell ([tools/shfuzz.py](https://github.com/kt97679/relf/blob/article-2026/tools/shfuzz.py)): на 827 из них dash и bash согласны, и relfsh согласен с ними; остальные 173 не учитываются. То, что генератор умеет находить расхождения, видно по yash: на 150 программах их девять, все законные — в `echo` и арифметике;
  - мутационное тестирование скомпилированного образа: из 30 случайных замен опкодов (из 3699 возможных мест) тесты ловят 20, а остальные 10 ничего видимого не меняют;
  - тестовые скрипты самого проекта (все файлы tests/shell/run-\*) исполняет не /bin/sh, а relfsh;
  - сигнальные штормы: сигнал каждые 2 мс во время конвейеров и подстановок команд — trap срабатывает, а результаты не искажаются;
  - реальные скрипты: configure от zlib отрабатывает так же, как под dash, а configure от ncurses (32301 строка, сгенерированная autoconf) создает 1041 файл, из которых 1040 совпадают с результатом dash, а в оставшемся config.status отличаются только две строки — те, где autoconf записал, как echo конкретного shell подавляет перевод строки.

Чего здесь нет:

- Это не сертифицированный POSIX shell: соответствие стандарту подтверждено только тестами, о которых шла речь выше.
- Это не полная система Forth 2012: только CORE и то, что нужно shell.
- Чисел с плавающей точкой нет: `printf '%.2f'` не поддерживается — POSIX позволяет printf обходиться без нее.
- Скрипты исполняются медленно — цифры приведены выше.
- Движок на ассемблере есть только для x86-64. Движок на C работает на x86-64, i386 и ARMv7, а под qemu — на AArch64 и RISC-V.
- Локалей нет, и shell везде считает время в UTC.

Теперь о том, как все это делалось. Начиная с конца августа 2026 года почти весь код, тесты и документацию — около 650 коммитов — написал Claude, ИИ-модель, в нескольких сотнях пронумерованных итераций под моим руководством. Я ставил цели, принимал решения (тридцать два из них записаны в [docs/QUESTIONS.md](https://github.com/kt97679/relf/blob/article-2026/docs/QUESTIONS.md)) и проверял каждую итерацию: перед каждым коммитом Claude прогонял полную проверку в своем окружении (x86-64, Linux), а затем я — на ноутбуке ThinkPad P14s Gen 5 (AMD Ryzen 7 PRO 8840HS) и на плате с ARMv7 (NVIDIA Tegra). Модель ошибается, как и человек, поэтому в проекте столько тестов. Журнал всех итераций, включая ошибки, лежит в [docs/PROGRESS.md](https://github.com/kt97679/relf/blob/article-2026/docs/PROGRESS.md).

Попробовать можно так:

```
git clone -b article-2026 https://github.com/kt97679/relf
cd relf
make relfshasm64 && ./relfshasm64   # x86-64 Linux, статический
make relfsh && ./relfsh             # другие процессоры: движок на C
```

Ветка `article-2026` — та версия, которую описывает статья, и в нее попадают только исправления; разработка продолжается в `master`. `make test` прогоняет основные тесты — CORE и тесты shell для обеих разрядностей и сравнение с bash, а `make verify` — все наборы, включая тесты движка на ассемблере, и сверяет результаты с `tests/BASELINE`. Как и просто `make`, оба собирают еще и движок с 4-байтовой ячейкой, для которого на x86-64 в Debian и Ubuntu нужен пакет gcc-multilib. Подробности сборки — в [README](https://github.com/kt97679/relf/blob/article-2026/README.md).

# relfsh: POSIX shell, написанный на форте

Я давно являюсь поклонником форта. Эта статья о том, что из этого в итоге выросло: relfsh — POSIX shell, написанный на форте. Это один статический файл размером 137612 байт, который в простое занимает около 200 КБ памяти и который можно расширять изнутри, на форте, прямо во время работы. Под ним лежит небольшая форт система, которая компилирует сама себя, а ее движок для x86-64 собирается из исходника на форте ассемблером, который тоже написан на форте.

Больше всего в форте меня восхищает то, что один человек за несколько дней может поднять работающую форт систему на новой платформе. Целиком, вместе с компилятором, и при этом вся система достаточно мала, чтобы уместиться в одной голове.

В девяностых я познакомился с форт системой sod32, написанной [Lennart Benschop](https://github.com/lennart-benschop): маленькая виртуальная машина, которая исполняет двоичный образ, не зависящий от платформы. Мне она показалась очень красивой. У нее было два недостатка: ограничения, заложенные в сам дизайн, и скорость. RelF (Relative Forth) начинался как моя попытка их исправить. Попытка удалась, но прирост скорости оказался скромным, и через какое-то время я отложил проект.

Тем временем меня не отпускала другая мысль: shell — очень недооцененный инструмент. Большая часть «клея» в наших системах, то есть кода, который связывает между собой программы, файлы и процессы, — это ровно то, в чем shell хорош. Если писать такой клей на Python, он становится длиннее, а каждая лишняя строка — это еще одно место для ошибки. Но и у POSIX shell есть два своих недостатка: расширять его можно только внешними программами — bash, ksh93 и zsh умеют загружать встроенные команды, но написанные на C под их собственные заголовки, — а структур данных в нем практически нет.

Здесь две идеи и встретились. Shell, написанный на форте, может быть маленьким и экономным, потому что таков сам форт. И его можно расширять изнутри, на самом форте, если дать ему подходящую встроенную команду.

Вот как это выглядит:

```
$ ./relfshasm64
$ forth '2 3 + . CR'
5
$ forth 'S" examples/seq.4" INCLUDED'
$ seq 1 3 | while read n; do echo "line $n"; done
line 1
line 2
line 3
```

Встроенная команда `forth` дает доступ ко всей форт системе, на которой написан shell. В этом примере `seq` — новая встроенная команда: дюжина строк на форте в файле `examples/seq.4`, которых нет в самом бинарнике; файл загружается во время работы, и дальше команда работает как любая другая. В каталоге [examples](https://github.com/kt97679/relf/tree/master/examples) есть еще хук для приглашения командной строки, TCP эхо сервер и HTTP сервер — все на форте и все внутри shell. Если положить строку с `forth` в файл, который называет `$ENV`, команда будет на месте при каждом запуске.

Вот сам `seq`, без двух строк `SEQ-NUM`, которые читают десятичное число, — это весь интерфейс встроенной команды: аргументы через `ARGC` и `ARGV@`, код возврата через `LAST-STATUS` и `BUILTIN`, чтобы дать ей имя.

```
: DO-SEQ ( --- )
  ARGC @ 3 < IF S" usage: seq FIRST LAST" ERR-TYPE ERR-NL 2 LAST-STATUS ! EXIT THEN
  2 ARGV@ SEQ-NUM 1+  1 ARGV@ SEQ-NUM
  2DUP > IF ?DO I N>STR DUP CSTRLEN TYPE CR LOOP ELSE 2DROP THEN
  0 LAST-STATUS ! ;
' DO-SEQ S" seq" BUILTIN
```

Ошибка в таком коде приводит к неудаче только этой команды, как это бывает с любой встроенной командой: `$?` равен 1, сообщение уходит в стандартный поток ошибок, а shell продолжает работать. Это касается и деления на ноль или обращения за пределы памяти shell: движок превращает аппаратное исключение процессора в фортовый THROW. Но то, чего никакая проверка не видит, остается опасным: запись в собственную память shell может его уронить — так же, как неудачная загружаемая встроенная команда роняет bash.

В остальном это обычный POSIX sh: конвейеры, списки, составные команды, функции, here-документы, все виды подстановок, управление заданиями, редактор командной строки с историей, поиском и автодополнением, а также `$'...'` и `set -o pipefail` из POSIX.1-2024.

Кто-то спросит, кому это может пригодиться, кроме любителей форта. Мне видятся три случая. Первый — минимальные окружения: на x86-64 статический shell без libc, размером со статический dash, но расширяемый на месте, может пригодиться в initramfs — рядом с утилитами, которые иначе принес бы busybox, — или в контейнере без базового образа. Второй — скрипты, которым не хватает структур данных: недостающее можно дописать на форте в виде встроенных команд и вызывать без порождения процессов. Третий — учебный: на x86-64 весь стек, от ассемблера до shell, написан на форте и воспроизводит сам себя.

Устроено все так:

```text
./relfshasm64 - один статический файл, 137612 байт
+------------------------------------------------+
| shell: парсер, исполнитель, редактор строки    |
|   shell.4  tree.4  edit.4          (форт)      |
+------------------------------------------------+
| форт: ядро, компилятор, расширения             |
|   kernel.4  extend.4  ...          (форт)      |
+------------------------------------------------+
| движок: 15592 байта кода x86-64, без libc      |
|   или движок на C, где есть компилятор C       |
+------------------------------------------------+
```

Shell и форт — это один двоичный образ с байт-кодом, а исполняет его движок. Движков два, и они исполняют один и тот же образ: переносимый, написанный на C, и написанный на ассемблере x86-64, который работает напрямую через системные вызовы. На x86-64 все наборы тестов прогоняются на обоих движках, и результаты должны совпадать.

Немного о форте, который лежит в основе.

- Шитый код на токенах: 64 однобайтовых опкода плюс дополнительные примитивы в виде двухбайтовых токенов: экранирующий байт и номер примитива (в RelF они называются «экранированными примитивами»). Высокоуровневые определения вызываются по смещению от начала образа — отсюда «Relative» в названии RelF, — поэтому образ работает, куда бы его ни загрузили. Вызов слова из первых 16 КБ образа занимает два байта, откуда бы его ни вызывали; любой другой — три и дотягивается до 4 МБ, поэтому образ и живет в области размером 4 МБ. Ядро — это первые 9824 байта образа, так что любой вызов ядра двухбайтовый.
- Свой образ для каждой разрядности ячейки: 8 или 4 байта, little-endian. Один образ работает на любой поддерживаемой машине своей разрядности.
- Форт компилирует сам себя: `cross.4`, работая на предыдущем образе ядра, компилирует `kernel.4` в следующий, и получается байт в байт тот же образ. gforth 0.7.3, исполняя тот же кросс-компилятор, выдает те же самые байты — то есть это проверка в духе [diverse double-compiling](https://arxiv.org/abs/1004.5534) — метода, которым David A. Wheeler предложил защищаться от атаки, описанной Ken Thompson в «Reflections on Trusting Trust».
- Что я могу утверждать: система проходит тесты CORE — набор тестов за авторством John Hayes ([tests/tester.fr](https://github.com/kt97679/relf/blob/master/tests/tester.fr)) с дополнениями из набора тестов Forth 2012, всего 2136 проверок — на обоих движках и для обеих разрядностей. Помимо CORE в ней есть то, что понадобилось shell. Другие наборы слов я не заявляю, а недостающие слова можно определить через встроенную команду `forth`.

Движок для x86-64 написан на форте ([`engine/relfasm64.4`](https://github.com/kt97679/relf/blob/master/engine/relfasm64.4)) при помощи ассемблера x86-64, который тоже написан на форте ([`forth/asm64.4`](https://github.com/kt97679/relf/blob/master/forth/asm64.4)) и использует постфиксный синтаксис:

```
rax [ rbx 8 ] mov,       \ mov rax, [rbx+8]
r12 [ r13 ] mov,         \ mov r12, [r13]
```

Цепочка сборки выглядит так:

```text
engine/cv8.c --cc--> relf64 (движок на C, один раз)
                        |
kernel.4 + cross.4 -----+--> kernel64.img  (воспроизводит себя)
                        |
relfasm64.4 + asm64.4 --+--> relfasm64     (15592 байт)
                            |
relfasm64.4, еще раз -------+--> relfasm64 (те же байты)
```

Движок на C собирается один раз и запускает ассемблер. Получившийся движок собирает сам себя повторно, и получаются те же 15592 байта. Вывод ассемблера сверяется с GNU as байт в байт на всех 456 формах инструкций, которые использует движок, а на случайных инструкциях всех форм, которые ассемблер поддерживает, — с точностью до равнозначной кодировки.

Проверка случайными инструкциями нашла ошибку при первом же запуске: `push`, `pop` и `xchg` с операндом в памяти молча собирались как инструкции с регистром. Это исправлено, и теперь такая проверка выполняется при каждой верификации.

Ближайший аналог, который я знаю, — [lbForth](https://github.com/larsbrinkhoff/lbForth), написанный Lars Brinkhoff: self-hosting форт с метакомпилятором, который раскручивается из нескольких строк на C.

Теперь о цифрах. Память в простое в КБ, по замерам [tools/mem-profile.py](https://github.com/kt97679/relf/blob/master/tools/mem-profile.py):

```text
                   резидентная  приватная
relfsh, движок asm         196        196
relfsh, движок C          1940        384
dash                      1968        100
busybox ash               1608        252
bash                      3704       1740
```

Каждый shell читает свой /proc/PID/smaps: резидентная память — это сумма Rss, куда входят и страницы, общие с другими процессами, прежде всего библиотека C; приватная — сумма Private_Clean и Private_Dirty. По резидентной памяти relfsh на своем движке меньше всех с большим отрывом: он не загружает библиотеку C. Если же считать только приватную память, dash использует вдвое меньше, чем relfsh.

Со скоростью нужно быть честным. Сначала shell: процессорное время (user+sys) относительно dash, медиана отношений по десяти раундам, в каждом из которых каждый shell прогонял каждую нагрузку ([tools/bench-vm.py](https://github.com/kt97679/relf/blob/master/tools/bench-vm.py)). В первой строке собственное время dash.

| процессорное время относительно dash | loop | fn | str | arith | realistic | start |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| dash, мс | 4,1 | 2,6 | 2,8 | 3,0 | 3,4 | 1,4 |
| busybox ash | 1,1× | 1,2× | 1,1× | 1,3× | 1,3× | 0,93× |
| bash | 2,1× | 2,4× | 2,2× | 2,4× | 2,8× | 1,3× |
| relfsh, движок asm | 25× | 22× | 20× | 27× | 27× | 0,56× |
| relfsh, движок C | 26× | 23× | 21× | 28× | 28× | 1,1× |

Нагрузки: loop — 2000 итераций проверки и инкремента; fn — 600 вызовов функции; str — 400 итераций `${s##*/}`, `${s%/*}` и `case`; arith — 700 шагов фибоначчи по модулю; realistic — разбор опций, обрезка строк, `case`, арифметика и `set --`, 300 итераций; start — один запуск `sh -c true`. На запуск relfsh тратит чуть больше половины того, что тратит dash, но скрипты исполняет в 20–28 раз медленнее: это интерпретатор байт-кода, а dash написан на C.

Теперь RelF как форт: семь небольших программ, один и тот же текст на форте для всех трех форт систем и те же алгоритмы на C, Go, Python и Ruby ([bench/langs/run.py](https://github.com/kt97679/relf/blob/master/bench/langs/run.py)). Время в миллисекундах, лучшее из трех запусков, включая запуск процесса; результат каждого запуска сверяется с результатом C. Последняя колонка — среднее геометрическое отношений ко времени RelF.

Семь маленьких программ — не рейтинг языков: они показывают, чего стоит эта виртуальная машина и где у нее слабые места. Обе таблицы измерены 27 сентября 2026 года на одном ядре Intel Xeon 2,1 ГГц.

Отдельно хочу рассказать о тестировании: от shell ждут очень точного поведения, и проверять его приходится с разных сторон.

- CORE: 2136 проверок, вывод обоих движков совпадает.
- Сам shell:
  - 1042 проверки в 91 файле;
  - 132 случая, где вывод сравнивается с bash;
  - 421 конструкция во всех контекстах в сравнении с bash и dash;
  - 48 случаев из POSIX, которые засчитываются только там, где все эталонные shell согласны между собой;
  - набор тестов из [mrsh](https://github.com/emersion/mrsh), другого маленького POSIX shell;
  - 44 сессии через псевдотерминал для редактора строки и управления заданиями;
  - примеры из самого стандарта POSIX, 64 штуки, с теми результатами, которые указаны в его тексте.
- Помимо наборов тестов:
  - семь shell «голосуют» по 131 скрипту, и relfsh оказывается на стороне каждого уверенного большинства;
  - 1000 случайных программ от генератора по грамматике shell ([tools/shfuzz.py](https://github.com/kt97679/relf/blob/master/tools/shfuzz.py)): там, где dash и bash согласны (827 программ; остальные 173 отложены), relfsh согласен с ними, а если вместо relfsh подставить yash, тот же генератор находит 9 расхождений на 150 программах — законных, в `echo` и арифметике yash, — так что находить их он умеет;
  - 131 сравнительный скрипт, каждый из которых переписан несколькими (до девяти) способами, не меняющими вывод, — всего 1170 вариантов;
  - мутационное тестирование скомпилированного образа;
  - тестовая обвязка, которую исполняет сам relfsh;
  - сигнальные штормы, в которых trap срабатывал на каждый посланный сигнал;
  - реальные скрипты: configure от zlib отрабатывает так же, как под dash, а configure от ncurses (32301 строка, сгенерированная autoconf) создает 1041 файл, из которых 1040 совпадают с результатом dash, а в оставшемся config.status отличаются только две строки — те, где autoconf записал, как echo конкретного shell подавляет перевод строки.
- Каждое изменение проверяется на трех машинах — двух x86-64 и плате с ARMv7 — прежде чем попасть в репозиторий.

Чтобы не было завышенных ожиданий, хочу сразу оговорить, чего здесь нет.

- Это не сертифицированный POSIX shell: соответствие стандарту подтверждено только тестами, о которых шла речь выше.
- Это не полная система Forth 2012: только CORE и то, что нужно shell.
- Плавающей точки нет: `printf '%.2f'` не поддерживается — POSIX позволяет printf обходиться без нее.
- Скрипты он исполняет медленно, цифры выше.
- Движок на ассемблере есть только для x86-64. Движок на C работает на x86-64, i386 и ARMv7, а под qemu — на AArch64 и RISC-V.
- Локалей нет, и время shell везде считает в UTC.

Предвижу вопрос о том, как все это делалось. Начиная с конца августа 2026 года почти весь код, тесты и документацию — около 650 коммитов — написал Claude, ИИ-модель, в нескольких сотнях пронумерованных итераций под моим руководством. Я ставил цели, принимал решения (тридцать два из них записаны в [docs/QUESTIONS.md](https://github.com/kt97679/relf/blob/master/docs/QUESTIONS.md)) и прогонял каждое изменение на своих машинах, прежде чем оно попадало в репозиторий. Модель ошибается, как и человек, поэтому в проекте столько тестов: ошибку в ассемблере с `push`, `pop` и `xchg`, о которой я писал выше, нашли именно они. Журнал всех итераций, включая ошибки, лежит в [docs/PROGRESS.md](https://github.com/kt97679/relf/blob/master/docs/PROGRESS.md).

Попробовать можно так:

```
git clone https://github.com/kt97679/relf
cd relf
make relfshasm64 && ./relfshasm64   # x86-64 Linux, статический
make relfsh && ./relfsh             # иначе: движок на C
```

`make test` прогоняет все наборы тестов. Как и просто `make`, он собирает еще и движок с 4-байтовой ячейкой, для которого на 64-битных Debian и Ubuntu нужен пакет gcc-multilib. Подробности сборки — в [README](https://github.com/kt97679/relf/blob/master/README.md).
